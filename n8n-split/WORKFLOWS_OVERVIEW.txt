================================================================================
 AUTOPULSE N8N WORKFLOWS — DETAILED TECHNICAL OVERVIEW
================================================================================

Scope: every workflow-N.json file in this folder (n8n-split/), one section each,
in numeric order. AutoPulse is an automotive-dealership CRM / lead-management
platform; these n8n workflows are the AI/automation backend behind inbound
email, SMS, ADF (XML lead format), campaign, and drafting/translation features.
The workflows are invoked over HTTP by a separate Node.js backend (see
aidmvcs-be-dev/ in this repo) — the workflows themselves never send email/SMS
or write to a primary datastore directly (except direct MongoDB reads); they
receive a webhook POST, run classification/generation logic (often via OpenAI
LangChain agent nodes), and return one JSON payload as the HTTP response,
which the calling backend then acts on (actually sending the message,
creating/updating a Lead record, etc.).

How to read the "Flow graph" sections below:
  [Node Name] (node type / one-line note)
    -> next node
  An indented "TRUE"/"FALSE" or labelled branch under an IF/Switch node shows
  which nodes run for each outcome. "TERMINAL" marks a node whose JSON becomes
  the workflow's HTTP response (all these workflows use responseMode=lastNode
  or an explicit Respond-to-Webhook node).

Generated by: automated analysis (six parallel research passes over the raw
workflow JSON via jq-based node/connection inspection), assembled into this
single file per user request. Any "anomaly"/"bug" notes below reflect what the
JSON actually contains, not confirmed production behavior — worth checking
against real n8n execution logs before treating any of them as certain.

## workflow-2.json — AutoPulse AI_SMS_Workflow_v5 (Multi Leads From One No)
================================================================================

**Purpose:** AutoPulse's core inbound-SMS conversational-AI engine for
automotive dealerships. Every inbound text message to a dealer's SMS number
lands here; the workflow reconstructs conversation/lead/inventory/campaign
context from MongoDB, runs it through a chain of GPT-4o-mini "agent" nodes to
classify intent, sentiment, DND status, language, communication preference
and extracted customer/vehicle data, then generates a single tone-and-CTA-
matched reply (SMS or, if the lead prefers, HTML email), decides an
appropriate lead/appointment status, and returns one JSON payload that the
calling backend uses to actually send the message and update the CRM. It
also has a full attachment-triggered sub-pipeline that downloads and
AI-analyzes images, PDFs/text documents, and videos sent by the customer to
enrich the reply context.

**Trigger:** Webhook — `POST /incoming-sms-messages` (node "SMS Trigger",
responseMode `lastNode`).

**Flow graph:**
```

  -> [Extract AI Bot Name & Store No] (Mongo: users, match dealer_account_information.sms_conversion_phone == recipient_number)
  -> [Set Bot Name & Store No & Store Address] (Set: AI Bot Name, Store No/Name/Address/Timezone/Website, Manager Name, Trade Link, Credit Finance)

**Step-by-step by branch:**

*1. Common preamble (every request):* SMS Trigger -> Input Extraction parses
the inbound payload shape `body.currentMessage.{content, message_id, sender,
recipient, date, dealer_id}`. Extract Attachments normalizes any MMS/media
attachments. Two identical Mongo lookups against `users` by
`dealer_account_information.sms_conversion_phone` pull the dealer's bot name,
store contact info/address/timezone/website, manager name, trade-in and
credit-application URLs, and weekly store hours (Format Store Hours renders
these into a plain-English string used later as a hard guardrail against the
AI proposing out-of-hours appointments). Check DB for existing query pulls
the full SMS thread from `emails` (bidirectional sender/recipient match) and
Extracting the context turns it into a chronological transcript string,
separately surfacing "lead notes" (is_note=true items) which the prompts are
told take precedence over transcript history.

*2. Classification chain:* Inquiry Classifier picks one of 14 granular
inquiry categories (Price/Availability/Test Drive/Financing/Trade-In/Service/
Warranty/Managerial Review/Hidden Price Concern/Sarcasm-Frustration/Already
Purchased/Closing/Negotiation/Delivery-Pickup) purely for tone/template
selection (via the static Intent Response Bank). Intent & Sentiment Analysis
is the decision-critical classifier: it decides between Visit
Requested/Suggested/Booked and Managerial Review (with an extensive
Tier-1/Tier-2 escalation-trigger rulebook — opt-out language, profanity,
PII/legal mentions, vehicle disputes, etc.) plus overall sentiment; this is
what routing IFs downstream key off of. Customer & Vehicle & Language Details
Extractor pulls structured name/email/phone/vehicle facts and detects the
customer's language (with rules to avoid mis-extracting greeting names or the
bot's own name). Communication Preference Detection flags if the customer
explicitly asked to be reached by SMS vs email. Format consolidates all of
this into one flat object that every downstream prompt and Set node
references by field name.

*3. Attachment sub-pipeline (If3 true):* Any attached image/video/document is
classified by MIME/extension, then routed through a Switch by modality.
Images are downloaded and sent to a GPT-4o-mini vision call with a strict
"only report what's visible" vehicle-inspection prompt, returning
vehicle_present/type/brand/damage/confidence. Documents split further: plain
text is decoded directly; PDFs are downloaded, saved to `/tmp/input.pdf`,
converted with the `pdftotext` CLI, and the resulting text file is read back
— both paths converge on a single "Analyze Text Attachment" GPT call that
extracts vehicle_model/year/vin/customer_name from the document text. Videos
are downloaded, saved, and processed with `ffmpeg` to extract 1 frame/second,
each frame independently run through the same vision prompt as images, then
aggregated (frame count, whether any frame flagged damage, average
confidence) before temp files are deleted. All three paths feed a 3-input
Merge, then Aggregate AI Insights and Build Response Context turn the
analysis into a human-readable "IMAGE ANALYSIS: ... / DOCUMENT ANALYSIS: ..."
string that later gets folded into the reply-generation prompts as
`safe_attachment_context`. Audio and "other"/archive attachments hit unwired
Switch outputs and are silently dropped (no analysis, no error).

*4. Lead/thread resolution:* Set Parent_Id determines whether this message
continues an existing thread (by finding the latest non-note prior message
and using its parent_message_id or message_id) or starts a new one (null ->
treated as a fresh lead). If1 branches on that: existing threads look up the
associated CRM `leads` record by parent_message_id to recover the VIN the
customer was discussing, then re-query the `vehicles` inventory collection
for that dealer+VIN and format a vehicle summary (year/make/model/trim/
engine/mileage/color/price/VDP link); it also fetches any related
email-channel history. New threads skip straight to lead-status
determination. Create or Update Lead Status then decides create_lead (true
only when there is no prior SMS AND no prior email context) vs update_lead.

*5. Campaign context:* Regardless of thread state, the workflow checks
whether this phone number recently received a delivered marketing campaign
SMS (`campaignleads` collection), dedupes matched campaign IDs, fetches those
`campaigns` documents, and picks the most recently sent one — its
subject/body get folded into `safe_campaign_context` so reply generators can
decide whether the incoming message is likely a reply to that campaign (with
explicit "don't assume intent when ambiguous" guidance in the prompts).

*6. Safety gate — DND:* DND Detection runs a dedicated GPT classifier against
Twilio-style STOP keywords, natural-language opt-out phrases, and "already
purchased elsewhere" signals, each with reason codes and confidence bands. If
dnd=="true", the flow terminates immediately at DND Response Formatting — no
customer-facing SMS is sent (`response: null`, `send_user_response: false`);
instead a manager alert SMS is generated (`send_manager_sms: true`)
summarizing the customer name, VDP link, and DND reason.

*7. Email-preference branch:* If the customer has explicitly asked for email
AND an email address is on file, Response Generation for Email Lead produces
a longer-form, HTML-styled email (subject + body) using the same tone/CTA
banks. Extract Email Response & Body strips markdown fences and parses the
JSON; Wrap HTML converts markdown bold to `<strong>`, strips any AI-inserted
`<a>` tags, splits into paragraphs, and auto-linkifies bare URLs, producing a
full HTML email body. This is a dead end (Response Formatting for Email
Lead), and note this is the only branch not passing through the 300-char SMS
trim.

*8. Managerial Review branch:* If the fine-grained `Format.intent` (from
Inquiry Classifier) is literally "Managerial Review", the flow bypasses the
LLM reply generator entirely and uses a canned English template ("A member
of our dealership team will connect with you shortly... view full vehicle
details here: <VDP or store website>"), plus a manager-alert SMS. Note: a
"Check if translation is needed" -> "Managerial Review Translation" ->
"Managerial Review Format" sub-chain exists in the JSON to translate this
canned message into the customer's detected language, but it has **no
inbound connection from anywhere in the graph** — it is orphaned/dead code
and never executes, so non-English customers currently receive the English
canned Managerial Review text (Managerial Review Response
Formatting.user_response is not localized despite `user_language` being set
on the output record).

*9. Visit-intent branch:* If intent contains "visit" (Requested/Suggested/
Booked) but isn't a Managerial Review, an inner If checks specifically for
"visit booked". If booked, Booking Response Generator (a scheduling-
specialist prompt with detailed ambiguous-date/time normalization rules —
e.g., inferring AM/PM, resolving "tomorrow"/weekday references against
today's date within store hours) emits `{sms_response, booking_date,
booking_time}`, which becomes a `booking_status: true` record with
`fe_lead_status: "Appointment Booked"` fixed. Otherwise (requested/suggested
but not yet booked), Visit Response Generator produces a reply, then a
second AI classifier (FE Lead Appointment Status2) inspects the conversation
+ generated reply to decide the current appointment_status (Booked/
Cancellation Requested/Reschedule Requested/No Appointment/Managerial
Review), and Set FE Lead Status 1 maps that into the `fe_lead` field used by
the CRM (falls back to "Lead" or "Contacted" based on create_lead).

*10. General-inquiry branch (default):* Anything not DND, not
email-preferred, not Managerial Review, not visit-related falls to Response
Generator — the main, most heavily-instructed prompt: one-sentence (<=160
char target, though the code trims to 300) replies, strict store-hours
enforcement, no re-pitching after explicit refusal, conditional VDP/trade-in/
credit-finance link inclusion, tone+CTA blending from the two static banks,
campaign-reply disambiguation, and multilingual response matching the
detected `languagename`. The same FE Lead Appointment Status -> Set FE Lead
Status pattern as branch 9 determines lead/appointment status before the
final Set node.

**Final outputs:** Because `responseMode` is `lastNode`, the HTTP response to
the webhook caller is whatever the terminating Set node in the executed
branch produced. All seven terminal Set nodes (Response Formatting, Visit
Response Formatting, Booking Response Formatting, DND Response Formatting,
Managerial Review Response Formatting, Response Formatting for Email Lead)
share a common field shape used by the calling system to actually dispatch
the message and update CRM state:
  - `lead_status` (free text status label, varies per branch)
  - `lead_name`, `lead_mail`, `lead_phone`, `sender_number`,
    `recipient_number`, `source` ("SMS")
  - `response` (the actual message text to send — null for DND/Managerial
    Review since those suppress or hard-code the customer message; HTML body
    for the email branch)
  - `message_id`, `request_query`/`request` (echo of inbound message),
    `parent_message_id`/`parent_id`
  - `create_lead`, `update_lead` (booleans for CRM upsert logic)
  - `fe_lead_status` (front-end/CRM lead pipeline stage)
  - `appointment_cancellation_requested` (bool)
  - `user_language`
  - Booking branch adds `booking_status`, `booking_date`, `booking_time`
  - DND/Managerial Review branches add `send_user_response`,
    `send_manager_sms`, `manager_sms` (and `user_response` for Managerial
    Review)
  - Email branch adds `response_mode: "email"`,
    `preferred_communication_mode_selected`, `preferred_communication_mode`,
    `preferred_communication_mode_old_messageID`

**Key integrations/side effects:**
- **OpenAI (via LangChain nodes), all `gpt-4o-mini`:** 12 chat-completion
  "agent" calls per full run, plus up to N vision/text calls in the
  attachment pipeline. None use n8n's structured output parser — every
  prompt is instructed to return raw JSON text which downstream Code/Set
  nodes manually `JSON.parse()` (with markdown-fence/newline stripping), so
  malformed LLM output would throw at that point.
- **MongoDB:** collections `users` (dealer/store config, queried twice),
  `emails` (SMS + email conversation threads), `leads` (VIN lookup by
  parent_message_id), `vehicles` (inventory by dealerId+VIN),
  `campaignleads` and `campaigns` (marketing campaign attribution).
- **Generic HTTP Request nodes** download attachment binaries from
  `{{$json.url}}` (likely a pre-signed S3/CDN link) with no fixed host baked
  into the workflow.
- **Local shell/CLI execution** (`n8n-nodes-base.executeCommand`) on the n8n
  worker: `pdftotext` for PDF-to-text extraction, `ffmpeg` for video frame
  extraction, and `rm` cleanup of temp files under `/tmp/` — meaning the n8n
  execution environment must have `poppler-utils` and `ffmpeg` installed,
  and this is a filesystem side effect on the worker host (fixed paths
  `/tmp/input.pdf`, `/tmp/output.txt`, `/tmp/input_video.mp4`,
  `/tmp/frame_*.jpg` — not safe for concurrent executions on the same
  worker, a potential race condition worth flagging).
- No direct SMS/email-sending integration (no Twilio/SES node) is present —
  it only *produces* the response payload and manager-alert flags; actual
  message dispatch and CRM persistence are the responsibility of whatever
  system consumes the webhook's JSON response.

## workflow-3.json — AutoPulse AI_Email_Workflow_v8 (Preferred Communication Mode)
================================================================================

**Purpose:** AutoPulse's central inbound-communications AI pipeline. A
Node.js backend POSTs every new inbound email/reply (and, for ADF-formatted
leads, phone/SMS-eligible leads) to this workflow. It parses the message
(plain text or ADF/XML lead format), pulls dealer/inventory/conversation
context from MongoDB, runs a chain of LLM agents to classify intent/
sentiment/DND/campaign-match/communication-preference, generates a
channel-appropriate (email or SMS) reply in the customer's detected
language, determines CRM lead/appointment status, and returns one
consolidated JSON payload the backend uses to actually send the reply and
update the CRM record. It also has a side pipeline that runs AI vision/OCR
analysis on email attachments (images, PDFs, text docs, videos) to enrich
the reply context. This is the workflow that the ADF-lead work earlier in
this session's history (`app/lib/adfLeadParser.js`,
`app/worker/emailWorker.js` in aidmvcs-be-dev) was built to partially bypass
for local, code-based extraction.

**Trigger:** `n8n-nodes-base.webhook` node **"Email Trigger"** — `POST
/incoming-email-messages`, response mode `lastNode`.

**Flow graph:**
```
[Email Trigger] (POST /incoming-email-messages)
  -> [Input Extraction] (Set: input_message, message_id, parent_id, create_lead, old_messages, dealer_id, subject, sender, has_attachments)
  -> [Extract Attachments] (Code: reads Email Trigger.body.currentEmail.attachments into a flat array)
  -> [Extract AI Bot Name & Store No & Store Name] (Mongo: users collection, _id = dealer_id)
  -> [Format Store Hours] (Code: builds store_hours_text from weekly_availability)
  -> [Set Bot Name & Store No & Store Name & Store Address] (Set: bot name, store no/name/address, website, timezone, manager name, trade/finance links)
  -> [Extract current date & time] (Code: today's date/time in dealer's timezone)
  -> [Check if its an ADF Lead] (IF: input_message contains "<adf>")

       ============================ TRUE: ADF / XML LEAD BRANCH ============================
       -> [Cleaning the Email] (Code: strips quoted-printable, isolates <?xml ...?> ... </adf>)
            *** references non-existent node "Decoding" — see anomaly note ***

**Step-by-step by branch:**

*Common preamble (runs for every request):*
1. **Email Trigger** — webhook `POST /incoming-email-messages`.
2. **Input Extraction** — Set node lifting `currentEmail`/`conversationThread`
   fields out of the webhook body: `input_message`, `message_id`, `parent_id`
   (parent conversation id — its presence/absence is the single most
   important routing signal in this workflow, driving If3/If4/If5),
   `create_lead` (true only if there's no prior conversation thread),
   `old_messages`, `dealer_id`, `subject`, `sender`, `has_attachments`.
3. **Extract Attachments** — re-reads attachments straight off `Email
   Trigger` (not off Input Extraction) into a normalized array
   (filename/content_type/size/url/s3_key/uploaded_at). Runs
   unconditionally, even for ADF leads.
4. **Extract AI Bot Name & Store No & Store Name** — MongoDB `users`
   collection, `_id = dealer_id`, pulls the dealer's AI-bot name, contact
   number, store name/address/website/timezone/manager name, trade-in and
   financing-application URLs, and weekly store hours.
5. **Format Store Hours** — builds a human-readable `store_hours_text`
   string from the weekly availability map.
6. **Set Bot Name & Store No & Store Name & Store Address** — Set node
   materializing the above into flat fields used throughout later prompts.
   Note: `Trade Link` and `Credit Finance` assignment expressions are
   missing a closing `}}` — likely a copy-paste bug that could cause these
   two fields to evaluate incorrectly or throw at runtime.
7. **Extract current date & time** — today's date/time formatted in the
   dealer's store timezone, used in nearly every generation prompt for
   "today"/"now" grounding.
8. **Check if its an ADF Lead** — `input_message` contains literal
   `"<adf>"`. This is the top-level fork between the ADF/XML branch and the
   plain-text/SMS branch.

*ADF branch (Automotive lead XML format — typically third-party lead
providers like AutoTrader/Cars.com):*
1. **Cleaning the Email** — strips quoted-printable artifacts and slices out
   the substring between `<?xml version="1.0" encoding="UTF-8"?>` and
   `</adf>`. **Bug/anomaly:** its first line reads
   `$node["Decoding"].json["cleanText"]`, but no node named `"Decoding"`
   exists in this workflow (only `"Decoding Mail Content"`, which actually
   runs *after* this node) — this reference will resolve to
   `undefined`/throw at execution time unless n8n silently no-ops it,
   meaning this node's real behavior in production should be verified
   against actual run logs.
2. **Decoding Mail Content** (Agent) — decodes any residual base64/
   quoted-printable, escapes reserved XML characters, and returns a single
   well-formed XML string.
3. **Sanitizing the xml** — regex fixups: closes malformed CDATA, escapes
   stray `&`, normalizes `<br>`/`<hr>`/`<img>` self-closing tags, strips
   BOM/NUL, normalizes smart quotes/dashes/nbsp.
4. **XML** (`n8n-nodes-base.xml`) — parses the sanitized string into JSON.
5. **ADF Lead** (Code) — deep-searches the parsed structure for
   `prospect`/`customer`/`vehicle`/vendor info regardless of nesting; picks
   the vehicle with `@interest="buy"` (or the first one if no interest
   attribute); extracts and normalizes name/email/phone; computes
   `send_sms` (valid phone present), `create_lead` (no valid phone but
   valid email), `update_lead` (valid name or email), and `vendorName`.
6. **ADF Comment Classifier & Extractor** (Agent) — parses the raw ADF
   `<comments>` block to separate the shopper's actual question from
   dealer/CRM boilerplate (VIN/MSRP/"Dealer note"/signatures), returning
   `is_user_query`, `user_query`, `confidence`, `reason`, plus language
   detection.
7. **Set ADF Comment & Language** — flattens to `customer_query` and
   `user_language`.
8. **If1** — has a VIN? If so, **Find Vehicles in Inventory** (Mongo
   `vehicles`, `dealerId`+`vin`) -> **Format Inventory Summary** (builds a
   structured + JSON-stringified vehicle summary incl. `vdplink`).
9. **Check if Customer Email is Present** — despite its name, this actually
   checks `ADF Lead.send_sms === true` (i.e., a valid **phone** number was
   found), routing phone-only leads to SMS and everyone else to email.
10. **Phone sub-branch:** **Response Generation for Phone Lead** generates a
    single-line SMS (<160 chars) using vehicle+comment+language ->
    **Limit Characters in Response** hard-truncates to 160 chars ->
    **Response Formatting for ADF Phone Lead** (terminal,
    `response_mode="sms"`, `lead_status="First Response Sent for ADF Phone
    Lead"`).
11. **Email sub-branch:** **Normalizing Vehicle Info** copies the inventory
    summary -> **Response Generator for ADF Lead** writes a warm sales-
    advisor email in the detected language -> **Extract Email Response &
    Body4** parses `{email_response, email_subject}` -> **Wrap HTML4**
    wraps in styled HTML -> **Response Formatting for ADF Lead** (terminal,
    `lead_status="ADF Lead"`, `create_lead=true`, `update_lead=true`,
    includes `vin`/`make`/`model`/`year`/`Lead_Source`=vendorName).

*Attachment-analysis sub-pipeline (only reached on the non-ADF path, and
only if `has_attachments == "true"`):* Same shape as workflow-2's pipeline
(classify -> flatten -> switch by modality -> image/document/video handling
via HTTP downloads, OpenAI vision, `pdftotext`, `ffmpeg` -> merge -> aggregate
-> build context string). **Anomaly:** n8n's Execute Command node
("cleanup") typically replaces its input JSON with `{stdout, stderr,
exitCode}` rather than passing through the prior item's fields, so the
`video_intelligence` object computed by Aggregate Video Intelligence is
likely lost before it reaches `Merge`. Separately, **Aggregate AI
Insights**'s code only buckets items where `modality === "image"` or
`"document"` — it has no handling for `modality === "video"` at all — so
even if the data survived, video insights would never appear in
`image_insights`/`document_insights`/`combined_context`. Net effect: video
attachments are downloaded and frame-analyzed by OpenAI, but that analysis
does not currently reach the reply-generation prompts.

*Context-assembly (non-ADF path, always runs):*
1. **If4** — has `parent_id` (existing thread)? If so, **Check DB for
   existing query** (Mongo `emails`, `communication_type="sms"` +
   `parent_message_id`) -> **Extracting the context** filters/formats SMS
   conversation history, honoring `use_replies_for_ai` (default allow
   unless explicitly false) and excluding internal notes, also extracting
   `lead_id` and any lead notes. If no `parent_id`, this step is skipped.
2. **Extract Old Messages** — formats `Email Trigger.body.conversationThread`
   into a `"Mail N:\n<content>"` text block (email thread history).
3. **Safe Context Merger** — combines SMS context, email context, and
   attachment context into `merged_sms_context`/`merged_email_context`/
   `merged_attachment_context`, each with a safe fallback string if missing.
4. **Cleaning Mail Content** (Agent) — strips headers/quoted-reply/signature
   from the raw `input_message`, returning only the first message's clean
   plain-text body. This cleaned text feeds essentially every downstream
   agent prompt as "Customer Query".
5. **Inquiry Classifier** — classifies into one of 13 intent buckets
   (Price/Availability/Test Drive/Financing/Trade-In/Service/Warranty/
   Managerial Review/Hidden Price Concern/Sarcasm-Frustration/Already
   Purchased/Closing/Negotiation/Delivery-Pickup, default "General
   Inquiry") + confidence (High/Med/Low).
6. **Intent Response Bank** — static Set node: a hardcoded JSON dictionary
   mapping each intent to a `tone` and a few example `templates`, used as
   style guidance (not verbatim text) for generation prompts.
7. **Customer & Vehicle & Language Details Extractor** — extracts
   name/email/phone/vehicle(make/model/year/mileage/condition)/language
   from the message body, with sender-metadata fallback for name/email
   only; returns all-blank fields if `create_lead` is false.
8. **Intent & Sentiment Analysis** — a second, escalation-aware intent
   classifier producing exactly one of `Visit Requested/Visit
   Suggested/Visit Booked/Managerial Review` plus `Positive/Neutral/
   Negative` sentiment; this (not Inquiry Classifier) drives the
   visit/booking/managerial-review IF nodes downstream.
9. **CTA_Templates_Bank** — static Set node: JSON dictionary of call-to-
   action phrase templates keyed by action and sentiment.
10. **Communication Preference Detection** — detects if the customer
    explicitly stated a contact-mode preference, returning
    `{has_preference, preferred_mode: "email"|"sms"}`.
11. **Format** — Set node consolidating essentially all AI-agent JSON
    outputs so far into flat fields (referenced pervasively downstream).
12. **Create or Update Lead Status** (Code) — re-parses the extractor
    output to compute `update_lead`, `create_lead` (true if valid phone, or
    valid email with no phone — but forced `false` if
    `Communication Preference Detection.preferred_mode === "sms"`), and
    `send_sms` (`create_lead && phone_valid`).
13. **If5** — has `parent_id`? True: **Check DB for VIN of the lead** ->
    **Extracting the VIN** -> **Find Vehicles in Inventory3** -> **Format
    Inventory Summary3**. False: **If2** — does `Format.make` exist? True:
    **Find Vehicles in Inventory1** -> **Format Inventory Summary1**. False:
    no inventory lookup.
14. **Safe Inventory Extractor** — picks whichever of Format Inventory
    Summary1/Summary3 succeeded (Summary1 preferred), else a "Vehicle
    information not available." fallback string — this becomes
    `safe_vehicle_info`, used across nearly all reply-generation prompts.

*DND (Do-Not-Disturb) branch:*
1. **DND Detection** — a "safety-first" classifier over the raw
   `input_message` (plus SMS/email context) that fires on Twilio
   STOP-keywords (STOP/STOPALL/UNSUBSCRIBE/CANCEL/END/QUIT/REVOKE/OPTOUT)
   or natural-language opt-out/already-bought/not-interested phrasing,
   returning `{dnd, reason, action, confidence}`.
2. **DND Extract** — flattens to `dnd`/`dnd_reason`.
3. **Check if DND is Opted** — `dnd == "true"`. True -> **DND Response
   Formatting** (terminal): `response=null`, `send_user_response=false` (no
   reply sent to the customer), `send_manager_sms=true` with a manager
   alert text including the DND reason and VDP link; `lead_status="DND"`,
   `fe_lead_status="DND"`. False -> proceeds to campaign matching.

*Campaign branch:*
1. **Aligning Email format for Campaign** — extracts the bare email address
   out of a `"Display Name <addr@domain>"` sender string, lowercased, as
   `clean_email`.
2. **Check DB if user was part of a campaign** — Mongo `campaignleads`,
   filtered on `dealer_id` + `clean_email` + `status="delivered"`.
3. **Removing duplication campaign ids** -> **Clean Campaign IDs** ->
   **Preparing Campaign Id arrays** — dedupes matched campaign IDs into a
   `{_id: {$in: [...]}}` Mongo query object.
4. **Find campaigns** — Mongo `campaigns`, using that query.
5. **Extracting the campaign details** — normalizes (strips Re:/Fwd:/
   bracketed tags) both the incoming email's subject and each candidate
   campaign's subject and looks for an exact match, returning
   `campaign_id/campaign_name/campaign_subject/campaign_body/
   use_replies_for_ai` (or nulls if no match).
6. **Find existing entries in DB using parent_id1** -> **Check Create Lead
   for Campaign1** — checks whether an `emailai` record already exists for
   this `parent_message_id`, producing a preliminary `create_lead` flag.
7. **Check if its a campaign response** — does `campaign_id` exist?
   - **TRUE (campaign-reply path):** **Extract lead details from campaign**
     -> **Extracting the lead name, email and phone from campaign** ->
     **Find existing entries in DB using parent_id** / **Check Create Lead
     for Campaign** -> **Campaign Response Generator** (Agent) writes an
     email reply that explicitly references the original campaign's
     subject/body plus tone/template/CTA guidance -> **Extract Email
     Response & Body3** -> **Wrap HTML3** -> **Campaign Response
     Formatting** (terminal: `lead_status`=Intent & Sentiment intent,
     `fe_lead_status="Contacted"`, plus `campaign_id`/`campaign_name`/
     `use_replies_for_ai`).
   - **FALSE:** falls through to Phone-Lead / Managerial-Review / Visit /
     General-Reply branches.

*Phone-lead (SMS) branch — non-ADF:*
1. **Check if it qualifies as Phone Lead** — OR condition: `Create or
   Update Lead Status.send_sms === true` OR `Communication Preference
   Detection.preferred_mode === "sms"`.
2. **Response Generation for Phone Lead1** — <160-char SMS using cleaned
   query, customer/vehicle info, store info, and intent/tone.
3. **Limit Characters in Response1** — hard truncate to 160 chars.
4. **FE Lead Appointment Status2** — classifies appointment status.
5. **Set FE Lead Status2** — `fe_lead` = the status if `"Appointment
   Bookedt"` (note: this literal has a typo — extra trailing "t" — so this
   branch never actually matches "Appointment Booked" and will always fall
   through to Lead/Contacted logic) else `"Lead"`/`"Contacted"` based on
   `create_lead`.
6. **Response Formatting for non-ADF Phone Lead** — terminal:
   `lead_status="First Response Sent for non-ADF Phone Lead"`,
   `response_mode="sms"`.

*Managerial Review branch:*
1. **Check if Managerial Review is needed** — AND condition: `Format.intent
   == "Managerial Review"` AND `has_attachments != "true"` (attachment-
   bearing messages are excluded from auto-escalation here, presumably
   because they get evaluated via the vision/OCR pipeline instead).
2. **Managerial Review Response Formatting** — terminal: `response=null`,
   `send_user_response=true` with a generic "a member of our team will
   reach out" holding message + VDP/website link, `send_manager_sms=true`
   with a "New Lead Needs Intervention" alert to the store manager,
   `fe_lead_status="Managerial Review"`.

*Visit / Booking branch:*
1. **Check if visit is intended** — `Intent & Sentiment Analysis.intent`
   contains `"visit"`.
2. **If** — does the intent further contain `"visit booked"`?
   - **TRUE:** **Booking Response Generator** confirms the visit and
     extracts `booking_date`/`booking_time` alongside an email
     subject/body -> **Extract Email Response & Body2** -> **Wrap HTML2**
     -> **Booking Response Formatting** (terminal: `booking_status=true`,
     `booking_date`, `booking_time`, `fe_lead_status="Appointment
     Booked"`, `appointment_cancellation_requested=false`).
   - **FALSE (visit requested/suggested but not yet confirmed):** **Visit
     Response Generator** writes a friendly reply referencing store hours
     and suggesting a visit -> **Extract Email Response & Body** -> **Wrap
     HTML1** -> **FE Lead Appointment Status1** re-classifies appointment
     status from the conversation + this new reply -> **Set FE Lead Status
     1** computes `fe_lead` + `appointment_cancellation_requested` ->
     **Visit Response Formatting** (terminal, `lead_status`=Intent &
     Sentiment intent).

*General reply branch (default/fallback — the most common path for
ordinary inquiries):*
1. **Response Generator** — the main general-purpose sales-advisor email
   generator: personalizes using inventory data, offers trade-in/finance
   links based on detected complex-finance/trade-in intent, mirrors the
   customer's language.
2. **Extract Email Response & Body1** — parses `{email_response,
   email_subject}`.
3. **Wrap HTML** — HTML-wraps the body (bold markdown -> `<strong>`,
   auto-linkifies URLs, paragraph splitting).
4. **FE Lead Appointment Status** — classifies appointment status from
   history + this reply.
5. **Set FE Lead Status** — `fe_lead` + `appointment_cancellation_requested`.
6. **Response Formatting** — terminal: `lead_status="First Response
   Sent"`, `response_mode="email"`, includes `preferred_communication_
   mode*` fields (only this and a few sibling terminal nodes carry these
   — used by the backend to know whether/when to switch channels for
   future replies).

**Final outputs (terminal Set nodes — each is a possible last-node HTTP
response):**

| Node | Trigger condition | Key fields |
|---|---|---|
| Response Formatting | Default general email reply | `lead_status="First Response Sent"`, `response_mode="email"`, `preferred_communication_mode*` fields, `fe_lead_status` |
| Visit Response Formatting | Visit requested/suggested, not yet booked | `lead_status`=AI intent, `fe_lead_status`, `response_mode="email"`, `preferred_communication_mode*` |
| Booking Response Formatting | Visit intent = "visit booked" | `booking_status=true`, `booking_date`, `booking_time`, `fe_lead_status="Appointment Booked"` |
| Managerial Review Response Formatting | Format.intent == "Managerial Review" & no attachments | `response=null`, `send_user_response=true` (holding msg), `send_manager_sms=true` (manager alert), `fe_lead_status="Managerial Review"` |
| Response Formatting for non-ADF Phone Lead | send_sms or SMS preference (non-ADF) | `lead_status="First Response Sent for non-ADF Phone Lead"`, `response_mode="sms"` |
| Response Formatting for ADF Lead | ADF lead, has email | `lead_status="ADF Lead"`, `create_lead=true`, `update_lead=true`, `vin/make/model/year`, `Lead_Source`=vendorName |
| Response Formatting for ADF Phone Lead | ADF lead, phone only | `lead_status="First Response Sent for ADF Phone Lead"`, `response_mode="sms"`, `vin/make/model/year`, `Lead_Source` |
| DND Response Formatting | Customer opted out | `response=null`, `send_user_response=false`, `send_manager_sms=true`, `lead_status="DND"` |
| Campaign Response Formatting | Subject matches a known marketing campaign | `lead_status`=AI intent, `fe_lead_status="Contacted"`, `campaign_id`, `campaign_name`, `use_replies_for_ai`, `response_mode="email"` |

Every one of these Set nodes also carries a common core: `lead_name`,
`lead_mail`, `lead_phone`, `source="Email"`, `message_id`, `create_lead`,
`update_lead`, `parent_id`, `request` (the customer's cleaned message),
`user_language`, `appointment_cancellation_requested`. The calling backend
is expected to branch on `response_mode` (`email`/`sms`) and
`send_user_response`/`send_manager_sms` flags to decide what to actually
dispatch.

**Key integrations/side effects:**
- **LLM calls:** 18 distinct GPT chat-model connections feeding 18
  LangChain Agent nodes, plus 3 direct "image/text analyze" nodes (all
  pinned to `gpt-4o-mini`). None of the agent nodes use a structured/JSON
  output parser — every agent returns free text that downstream Code/Set
  nodes manually `JSON.parse()` after stripping markdown fences and
  newlines, a recurring fragility point.
- **MongoDB:** 11 nodes hitting collections `users`, `vehicles`, `emails`,
  `leads`, `campaignleads`, `campaigns`, `emailai`.
- **HTTP Request nodes:** generic file downloads fetching attachment
  binaries from `{{$json.url}}`.
- **Shell/OS side effects:** `pdftotext` and `ffmpeg` invocations, writing/
  reading temp files under `/tmp/` and cleaning them up afterward —
  requires those CLIs installed on the n8n worker, and creates potential
  race conditions if concurrent webhook executions share the same fixed
  temp filenames.
- **Notable anomalies found during analysis (worth verifying against
  production logs):**
  1. `Cleaning the Email` references a nonexistent node `"Decoding"`
     (should be `"Decoding Mail Content"`, which in fact runs after it) —
     likely dead/broken code left over from a rename.
  2. `Set Bot Name & Store No & Store Name & Store Address`'s `Trade Link`
     and `Credit Finance` field expressions are missing a closing `}}`.
  3. The video-analysis path's `Aggregate Video Intelligence` output is
     likely discarded by the subsequent `cleanup` Execute Command node
     before reaching `Merge`, and even if it survived, `Aggregate AI
     Insights` has no handling branch for `modality === "video"` — so video
     attachment analysis currently doesn't influence the generated reply.
  4. `Set FE Lead Status2` checks for the literal string `"Appointment
     Bookedt"` (typo) instead of `"Appointment Booked"`, so the phone-lead
     SMS path never correctly reports a booked appointment via that node.
  5. The node named `"Check if Customer Email is Present"` (ADF branch)
     actually tests for a present **phone number** (`send_sms`), not an
     email — a misleading name, not a functional bug.

## workflow-4.json — AutoPulse AI_SMS_Workflow_v6 (VDP URL)
================================================================================

**Purpose:** The inbound-SMS conversational AI engine for AutoPulse. It
receives an incoming customer text message via webhook, runs it through a
chain of OpenAI-backed LangChain agents to classify intent/sentiment/
inquiry-type and extract customer & vehicle details, pulls prior SMS/email
conversation history and matched vehicle inventory from MongoDB, and
produces one of five kinds of formatted reply payloads (general reply,
visit-related reply, booking confirmation, managerial-escalation notice, or
an HTML email reply) which n8n returns synchronously as the webhook response
for a downstream system to actually dispatch. It also derives CRM
lead-status fields (create/update lead, FE lead status) as a side effect of
each conversation turn.

**Trigger:** Webhook — `POST /incoming-sms-messages` (responseMode:
`lastNode`).

**Flow graph:**
```
[Webhook: POST /incoming-sms-messages] (SMS Trigger)
  -> [Input Extraction] (Set: pulls input_message, message_id, sender_number, recipient_number, received_date, dealer_id from body.currentMessage)
  -> [Extract AI Bot Name & Store No] (Mongo "users": find by dealer_account_information.sms_conversion_phone == recipient_number)
  -> [Set Bot Name & Store No & Store Address] (Set: AI Bot Name, Store No, Store Name, Store Address, Store Timezone)
  -> [Inquiry Classifier] (LLM agent, gpt-3.5-turbo)
  -> [Intent Response Bank] (Set: static JSON lookup table of tone+template pairs per intent category)
  -> [Customer & Vehicle Details Extractor] (LLM agent, gpt-3.5-turbo)
  -> [Intent & Sentiment Analysis] (LLM agent, gpt-3.5-turbo)
  -> [Communication Preference Detection] (LLM agent, gpt-3.5-turbo)
  -> [Format] (Set: consolidates category/intent/sentiment/Name/Email/Phone/make/model/year/mileage/condition from the three agent outputs)
  -> [Check DB for existing query] (Mongo "emails": find where (sender=sender_number AND recipient=recipient_number) OR reversed, limit 100)
  -> [Extracting the context] (Code: builds a human-readable SMS conversation transcript string from received/sent/failed messages)
  -> [Set Parent_Id] (Code: sorts fetched messages by timestamp desc, returns parent_message_id or message_id of latest, or null)
  -> [If1] (IF: parent_id notEmpty?)
       TRUE  -> [Check DB for VIN of the lead] (Mongo "leads": find by parent_message_id == parent_id)
             -> [Extracting the VIN] (Code: extracts vin field only)
             -> [Find Vehicles in Inventory] (Mongo "vehicles": find by dealerId + vin)
             -> [Format Inventory Summary] (Code: builds vehicleData object — has a JS syntax bug, see note below)
             -> [Check DB for existing query1] (Mongo "emails": find by communication_type=email AND parent_message_id, limit 100)
             -> [Extracting the context1] (Code: builds email conversation transcript string)
             -> [Create or Update Lead Status] (Code: sets create_lead/update_lead booleans)
       FALSE -> [Create or Update Lead Status] (same node, reached directly — no VIN/inventory lookup)
  -> [Extract current date & time] (Code: today's date/time in dealer's Store Timezone)
  -> [Safe Context Extractor] (Code: safe_sms_context / safe_email_context, with fallback text if missing)
  -> [Safe Inventory Extractor] (Code: safe_vehicle_info, falls back to "Vehicle information not available.")
  -> [Check if it qualifies as Email Lead] (IF: preferred_mode == "email" AND Format.Email notEmpty)
       TRUE  -> [Response Generation for Email Lead] (LLM agent, gpt-3.5-turbo)
             -> [Extract Email Response & Body] (Code: parses/cleans email_response + email_subject JSON)
             -> [Wrap HTML] (Code: wraps email_response into styled HTML with linkified URLs and bold fixups)
             -> [Response Formatting for Email Lead] (Set) [TERMINAL]
       FALSE -> [Check if Managerial Review is needed] (IF: Intent&Sentiment output.intent, lowercased, contains "managerial review")
             TRUE  -> [Managerial Review Response Formatting] (Set) [TERMINAL]
             FALSE -> [Check if visit is intended] (IF: Intent&Sentiment output.intent, lowercased, contains "visit")
                   TRUE  -> [If] (IF: same intent contains "visit booked")
                         TRUE  -> [Booking Response Generator] (LLM agent, gpt-4o-mini)
                               -> [Extract Booking Response] (Set: parses sms_response)
                               -> [Limit Characters in Booking Response] (Code: slice to 160 chars)
                               -> [Booking Response Formatting] (Set) [TERMINAL]
                         FALSE -> [Find available slots] (Mongo "users": same dealer lookup, fetches weekly_availability)
                               -> [Format Store Hours] (Code: builds store_hours_text from weekly_availability)
                               -> [Visit Response Generator] (LLM agent, gpt-4o-mini)
                               -> [Extract Visit Response] (Set: parses sms_response)
                               -> [Limit Characters in Response1] (Code: slice to 160 chars)
                               -> [FE Lead Appointment Status2] (LLM agent, gpt-3.5-turbo)
                               -> [Set FE Lead Status 1] (Code: fe_lead = "Lead" or "Contacted" based on create_lead)
                               -> [Visit Response Formatting] (Set) [TERMINAL]
                   FALSE -> [Response Generator] (LLM agent, gpt-4o-mini)
                         -> [Limit Characters in Response] (Code: slice to 160 chars)
                         -> [FE Lead Appointment Status] (LLM agent, gpt-3.5-turbo)
                         -> [Set FE Lead Status] (Code: fe_lead = "Lead" or "Contacted")
                         -> [Response Formatting] (Set) [TERMINAL]
```

**Step-by-step by branch:**

*Ingestion & NLU (shared prefix, all branches):*
1. `SMS Trigger` receives the raw payload from an upstream SMS gateway/
   middleware.
2. `Input Extraction` flattens `body.currentMessage.*` into top-level fields
   used throughout.
3. `Extract AI Bot Name & Store No` looks the dealer up in MongoDB `users`
   by matching the SMS number the message was sent to, establishing tenant
   context (multi-dealer support).
4. `Set Bot Name & Store No & Store Address` composes bot name, store
   contact number, name, a concatenated full address string, and timezone
   for later prompts.
5. `Inquiry Classifier` buckets the message into a fixed set of inquiry
   categories (Price, Availability, Test Drive, Financing/Loan, Trade-In,
   Service, Warranty, Managerial Review, General) with a confidence level.
   It does **not** see conversation history in this file (see workflow-6
   for the context-aware variant).
6. `Intent Response Bank` is a static Set node containing a hard-coded
   lookup table (9 categories) of `{tone, templates[]}`.
7. `Customer & Vehicle Details Extractor` pulls name/email/phone and
   vehicle make/model/year/mileage/condition out of the raw message text.
8. `Intent & Sentiment Analysis` classifies visit-related intent (`Visit
   Requested` / `Visit Suggested` / `Visit Booked` / `Managerial Review`)
   plus sentiment. The Managerial Review escalation guidance here is
   comparatively narrow (last-resort only).
9. `Communication Preference Detection` detects an explicit stated
   preference for SMS vs email contact.
10. `Format` merges all three agent outputs plus the classifier category
    into one flat object.
11. `Check DB for existing query` searches the `emails` collection (used as
    a generic message-log store keyed by phone numbers) for prior SMS
    traffic between these two numbers.
12. `Extracting the context` turns any found records into a readable
    transcript string.
13. `Set Parent_Id` picks the most recent record and derives a `parent_id`
    (its own `parent_message_id`, or its `message_id` if it's a root
    message), or `null` if no history exists.
14. `If1` branches on whether a `parent_id` was found.

*Branch A — existing conversation (If1 TRUE):*
15. `Check DB for VIN of the lead` looks up a `leads` record by
    `parent_message_id` to recover which vehicle this thread is about.
16. `Extracting the VIN` pulls just the `vin` field.
17. `Find Vehicles in Inventory` queries `vehicles` by `dealerId` + `vin`.
18. `Format Inventory Summary` builds a `vehicleData` object (year, make,
    model, trim, body, engine, mileage, colors, price, etc.). **Bug:** the
    code is `price: item.internetprice || null\n  shortUrl: item.shortUrl
    || null\n};` — missing comma between `null` and `shortUrl` is a
    JavaScript syntax error, so this Code node will throw at runtime and
    this entire lookup path (any returning customer whose message resolves
    to a known VIN) breaks. Also note it stores the field as `shortUrl`,
    not `vdplink` — nothing downstream in this file's prompts actually
    reads `shortUrl`, so even if the syntax were fixed, no VDP link would
    ever reach the customer response despite the workflow's "(VDP URL)"
    name.
19. `Check DB for existing query1` / `Extracting the context1` repeat the
    context-building step but scoped to `emails` records with
    `communication_type: "email"`.
20. `Create or Update Lead Status` decides `create_lead` (true only if no
    SMS and no email context exist at all) and `update_lead` (true if not
    creating and a name/email was extracted).

*Branch B — new conversation (If1 FALSE):* skips directly to `Create or
Update Lead Status` with both `context` values effectively absent, so
`create_lead` is typically true.

*Shared continuation:*
21. `Extract current date & time` computes "today"/"now" in the dealer's
    timezone.
22. `Safe Context Extractor` / `Safe Inventory Extractor` wrap the SMS
    context, email context, and vehicle info with human-readable fallback
    strings so downstream prompts never see `undefined`.
23. `Check if it qualifies as Email Lead` — routes to the email branch only
    when the customer expressed an email preference AND an email address
    was actually captured.

*Branch: Email Lead (TRUE):*
24. `Response Generation for Email Lead` writes a warm sales-style email
    body + subject.
25. `Extract Email Response & Body` strips markdown/code-fences and parses
    the JSON reliably.
26. `Wrap HTML` converts the plain email text into a styled HTML document.
27. `Response Formatting for Email Lead` assembles the final terminal
    object: `lead_status "First Response Sent"`, `response` = the HTML
    body, `fe_lead_status = "Lead"`, `response_mode = "email"`.

*Branch: Managerial Review (Email-lead FALSE, Managerial-review TRUE):*
28. `Check if Managerial Review is needed` tests whether `Intent &
    Sentiment Analysis`'s intent (lower-cased) contains "managerial
    review".
29. `Managerial Review Response Formatting` sets `lead_status`/
    `fe_lead_status` = "Managerial Review", `response` = null — i.e. it
    records the escalation in the CRM but (unlike workflow-6) does **not**
    compose an automatic customer reply or a manager alert SMS.

*Branch: Visit-related (Managerial-review FALSE, visit-intent TRUE):*
30. `Check if visit is intended` tests intent contains "visit".
31. `If` (visit-booking sub-check) tests intent contains "visit booked".
    - **Booking sub-branch (TRUE):** `Booking Response Generator` confirms/
      extracts booking date & time; `Extract Booking Response` parses
      `sms_response`; `Limit Characters in Booking Response` truncates to
      160 chars; `Booking Response Formatting` builds the terminal payload
      including `booking_status: true`, `booking_date`, `booking_time`,
      `fe_lead_status`: "Appointment Booked".
    - **Visit-suggestion/request sub-branch (FALSE):** `Find available
      slots` re-fetches the dealer's `weekly_availability`; `Format Store
      Hours` turns it into a readable hours string; `Visit Response
      Generator` composes a reply; `Extract Visit Response` parses
      `sms_response`; `Limit Characters in Response1` truncates to 160
      chars; `FE Lead Appointment Status2` re-reads the conversation +
      generated reply to classify appointment state — note its JSON output
      isn't actually consumed downstream (the consuming code is commented
      out in `Set FE Lead Status 1`); `Set FE Lead Status 1` sets `fe_lead`
      to "Lead" or "Contacted" purely from `create_lead`; `Visit Response
      Formatting` builds the terminal payload with `lead_status` = the
      detected intent string.

*Branch: General inquiry (visit-intent FALSE, the default/fallback path):*
32. `Response Generator` — the main-line reply generator — answers using
    inventory/context/customer info.
33. `Limit Characters in Response` truncates to 160 chars.
34. `FE Lead Appointment Status` re-classifies appointment state (same
    4-state schema) — again unused by the immediately following code
    (commented out).
35. `Set FE Lead Status` sets `fe_lead` = "Lead"/"Contacted" from
    `create_lead`.
36. `Response Formatting` builds the terminal payload: `lead_status` =
    "First Response Sent", `response` = truncated SMS text, plus all
    identifiers.

**Final outputs:** The webhook always returns exactly one JSON object —
whichever of the five `*Formatting` Set nodes was last executed. Each
carries a common core (`lead_status`, `lead_name`, `lead_mail`,
`lead_phone`, `source`, `response`, `message_id`, `request_query`,
`create_lead`, `update_lead`, `parent_id`/`parent_message_id`,
`sender_number`, `recipient_number`, `fe_lead_status`) plus branch-specific
fields (booking date/time, email response_mode/subject, etc.).

**Key integrations/side effects:**
- MongoDB collections read: `users` (×2), `emails` (×2), `leads`,
  `vehicles`. No writes are performed inside this workflow.
- OpenAI via LangChain agent nodes (10 agents total): `gpt-3.5-turbo` used
  for Inquiry Classifier, Customer & Vehicle Extractor, Intent & Sentiment
  Analysis, Communication Preference Detection, both FE Lead Appointment
  Status agents, Response Generation for Email Lead; `gpt-4o-mini` used for
  the three primary reply generators.
- No other outbound HTTP Request nodes are present.
- Notable bug: `Format Inventory Summary`'s JS has a missing comma (syntax
  error) that would crash the returning-customer/VIN-lookup path at
  runtime.

## workflow-5.json — "My workflow 2"

**Purpose:** A manually-triggered debug/logging utility. It formats an
arbitrary JSON payload into a single log line and appends that line to a
local log file on the n8n host via a shell command. Not tied to any
AutoPulse business logic (leads, dealers, etc.) — looks like a generic
developer testing/scratch workflow for verifying n8n logging mechanics.

**Flow graph:**
```
Start -> Format Log -> Write Log to File
```

   Produces an empty/default input item to kick off the chain.

   ```js
   const logLine = `[${new Date().toISOString()}] Type=${$json.type || 'info'} | Stage=${$json.stage || 'unspecified'} | RunId=${$json.runId || $runId} | Data=${JSON.stringify($json.data || {})}`;

   command:
   ```
   echo "{{$json["logLine"]}}" >> ~/n8n-logs.log
   ```
   Appends the formatted log line to `~/n8n-logs.log` on the machine
   running n8n.

**Final outputs:** No data returned to a caller (no webhook, no respond
node) — the only effect is a side effect: one line appended to
`~/n8n-logs.log` each time the workflow is manually run.

**Step-by-step by branch:**

*Ingestion & NLU (shared prefix — reordered vs. workflow-4):*
1. `SMS Trigger` / `Input Extraction` / `Extract AI Bot Name & Store No` are
   identical to workflow-4.
2. `Set Bot Name & Store No & Store Address` additionally captures `Store
   Website` and `Manager Name`, used later for the VDP-fallback and
   manager-alert text.
3. Unlike workflow-4, `Check DB for existing query` and `Extracting the
   context` run **before** the NLU agents, so conversation history is
   available to them.
4. `Inquiry Classifier` — same category scheme as workflow-4, but its
   prompt now also includes "Old Conversation Context."
5. `Intent Response Bank` (Set) — same base categories as workflow-4 plus
   six more: **Hidden Price Concern, Sarcasm/Frustration, Already
   Purchased, Closing, Negotiation, Delivery/Pickup**. **Bug:** the

   concatenated back-to-back rather than one merged object, i.e.

   node's output whenever it executes.
6. `Intent & Sentiment Analysis` — same 4-state visit intent + 3-state
   sentiment output schema as workflow-4, but the prompt is far more
   elaborate: it now also receives "Old Conversation Context," explicitly
   instructs the model to "maximize recall for escalation" (favor
   Managerial Review when in doubt, even over a visit intent), and defines
   nine broad escalation trigger categories (A-J): opt-out/stop/human
   requests, customer no longer in market, vehicle unavailable/disputed,
   negative/risky sentiment, ambiguous references to prior context,
   compliance/PII/legal concerns, operational risk, vehicle-history report
   requests, location/no-follow requests, and a large "filter-out" list of
   topics that must always escalate (financing/leasing, rebates/incentives,
   taxes/fees/DMV, warranty/protection plans, vehicle history reports,
   trade-in/appraisal, EV/hybrid specifics, after-sales/service,
   legal/compliance, fleet/commercial). This makes the bot far more
   conservative about auto-answering anything beyond basic price/

not send anything itself — it returns a structured JSON payload (lead/CRM
fields + rendered response) to whatever backend called the webhook, which

2. **Input Extraction** flattens the relevant fields into top-level
   properties for downstream nodes.
3. **Extract AI Bot Name & Store No & Store Name** looks up the dealer's

   into a human-readable string.
5. **Set Bot Name & Store No & Store Name & Store Address** stages dealer
   branding for prompt injection.
6. **Extract current date & time** computes "today" in the dealer's
   timezone for date-relative reasoning.
7. **Inquiry Classifier** and **Intent & Sentiment Analysis** run two
   independent LLM classifications: one for a granular topic bucket, one
   for sales-funnel stage + escalation risk.
8. **Intent Response Bank** / **CTA_Templates_Bank** are static Set nodes

9. **Format** consolidates both classifier outputs (with defensive JSON

*Branch D — Visit intended (not yet booked):* Generates a visit-suggestion

*Branch E — General inquiry (default):* No visit signal detected;

**Key integrations/side effects:** OpenAI `gpt-4o-mini` via 6 LangChain
Chat Model nodes feeding 6 Agent nodes. MongoDB direct queries against

a decision/content-generation engine whose JSON output is consumed by an
external caller.

                  -> [Customer & Vehicle Details Extractor] (Agent: extracts name/email/phone/vehicle{make,model,year,mileage,condition}, only if create_lead=true)
                  -> [Intent & Sentiment Analysis] (Agent: classifies intent as Visit Requested/Suggested/Booked/Managerial Review + sentiment, with Tier-1/Tier-2 escalation-trigger rules)
                  -> [CTA_Templates_Bank] (Set, raw JSON mode: static book_appointment/confirm_appointment/reschedule/visit_suggestion/info_followup/escalate templates x positive/neutral/negative)
                  -> [Communication Preference Detection] (Agent: has_preference + preferred_mode sms/email)
                  -> [Format] (Set: consolidates intent, sentiment, Name/Email/Phone/make/model/year/mileage/condition, ic_confidence/ic_intent/ic_tone/ic_templates, cta_templates)
                  -> [Create or Update Lead Status] (Code: computes update_lead, create_lead, send_sms booleans from name/phone/email validity + communication preference override)
                  -> [If5] (IF: Input Extraction.parent_id not empty)
                       TRUE  -> [Check DB for VIN of the lead] (Mongo: leads collection, parent_message_id=parent_id)
                             -> [Extracting the VIN] (Code: pulls vin field, default "VIN not found")
                             -> [Find Vehicles in Inventory3] (Mongo: vehicles, dealerId+vin)
                             -> [Format Inventory Summary3] (Code: vehicle_info JSON string)
                             -> [Safe Inventory Extractor] (Code: merges Format Inventory Summary1/3 into safe_vehicle_info, defaulting to "Vehicle information not available.")
                       FALSE -> [If2] (IF: Format.make not empty)
                             TRUE  -> [Find Vehicles in Inventory1] (Mongo: vehicles, dealerId + make/model from Format)
                                   -> [Format Inventory Summary1] (Code: vehicle_info JSON string)
                                   -> [Safe Inventory Extractor] (same node as above)
                             FALSE -> [Safe Inventory Extractor] (same node, no vehicle match -> default text)
                  -> [DND Detection] (Agent: opt-out/unsubscribe/already-bought classifier -> dnd, reason, action, confidence)
                  -> [DND Extract] (Set: dnd, dnd_reason)
                  -> [Check if DND is Opted] (IF: DND Extract.dnd === "true")
                       TRUE  -> [DND Response Formatting] === TERMINAL (response: null, send_user_response:false, send_manager_sms:true)
                       FALSE -> [Check if it qualifies as Phone Lead] (IF, OR: Create or Update Lead Status.send_sms===true OR Communication Preference Detection.preferred_mode==="sms")
                             TRUE  -> [Response Generation for Phone Lead1] (Agent: 1-line SMS <=160/300 chars w/ tone+CTA templates, optional VDP/booking link) [gpt-3.5-turbo]
                                   -> [Limit Characters in Response1] (Code: truncate to 300 chars)
                                   -> [FE Lead Appointment Status2] (Agent: appointment_status classification)
                                   -> [Set FE Lead Status2] (Code: fe_lead from appointment_status/create_lead — checks "Appointment Bookedt", a likely typo bug that never matches "Appointment Booked")
                                   -> [Response Formatting for non-ADF Phone Lead] === TERMINAL (response_mode: sms)
                             FALSE -> [Check if Managerial Review is needed] (IF: Format.intent === "Managerial Review")
                                   TRUE  -> [Managerial Review Response Formatting] === TERMINAL (response: null, send_user_response:true w/ escalation msg, send_manager_sms:true)
                                   FALSE -> [Check if visit is intended] (IF: Intent & Sentiment Analysis.intent contains "visit")
                                         TRUE  -> [If] (IF: Intent & Sentiment Analysis.intent contains "visit booked")
                                               TRUE  -> [Booking Response Generator] (Agent: confirms visit, extracts booking_date/booking_time)
                                                     -> [Extract Email Response & Body2] (Code: parse -> email_response/email_subject)
                                                     -> [Wrap HTML2] (Code: HTML wrap)
                                                     -> [Booking Response Formatting] === TERMINAL (booking_status:true, fe_lead_status:"Appointment Booked", response_mode: email)
                                               FALSE -> [Visit Response Generator] (Agent: friendly email reply, store hours/visit suggestion, VDP/booking link logic)
                                                     -> [Extract Email Response & Body] (Code: parse -> email_response/email_subject)
                                                     -> [Wrap HTML1] (Code: HTML wrap)
                                                     -> [FE Lead Appointment Status1] (Agent: appointment_status classification)
                                                     -> [Set FE Lead Status 1] (Code: fe_lead from appointment_status/create_lead)
                                                     -> [Visit Response Formatting] === TERMINAL (response = Wrap HTML1's HTML body, but response_mode is set to "sms" — likely inconsistency)
                                         FALSE -> [Response Generator] (Agent: general HTML email reply w/ tone+CTA templates, VDP/booking-link logic)
                                               -> [Extract Email Response & Body1] (Code: parse -> email_response/email_subject)
                                               -> [Wrap HTML] (Code: HTML wrap)
                                               -> [FE Lead Appointment Status] (Agent: appointment_status classification)
                                               -> [Set FE Lead Status] (Code: fe_lead from appointment_status/create_lead)
                                               -> [Response Formatting] === TERMINAL (lead_status:"First Response Sent", response_mode: email)
```

**Step-by-step by branch:**

*1. Common bootstrap (every request)* — mirrors workflow-3's preamble:
Input Extraction normalizes fields (`input_message`, `message_id`,
`parent_id`, `create_lead`, `old_messages`, `dealer_id`, `subject`,
`sender`); dealer/store lookup + store-hours formatting; current
date/time; then forks on whether `input_message` contains `<adf>`.

*2. ADF (XML) lead branch* — same overall shape as workflow-3's ADF branch
(Cleaning the Email -> Decoding Mail Content -> Sanitizing the xml -> XML
-> ADF Lead -> ADF Comment Classifier & Extractor -> Set ADF Comment ->
optional inventory lookup -> phone-vs-email split -> SMS or HTML email
reply). **Note:** `Cleaning the Email`'s code here also references
`$node["Decoding"]`, but no node named "Decoding" exists in this workflow
either — the same likely-leftover bug as workflow-3.

*3. Non-ADF branch (ordinary inbound email or SMS-thread reply)* — pulls
prior SMS-side context from MongoDB when `parent_id` is present, merges it
with the webhook-supplied email conversation thread, cleans the message
body, runs the same classification chain as workflow-3 (Inquiry Classifier,
Intent & Sentiment Analysis, Customer & Vehicle Details Extractor,
Communication Preference Detection), consolidates into `Format`, computes
`create_lead`/`update_lead`/`send_sms`, resolves vehicle-of-interest
inventory (by prior lead's VIN if replying in-thread, else by
newly-extracted make/model), then runs `DND Detection` as a safety gate
before routing into Phone-Lead / Managerial-Review / Visit-Booking /
General-Reply branches — functionally identical decision tree to
workflow-3's non-ADF path, with 8 possible terminal Set nodes.

**Final outputs:** The workflow always terminates in exactly one of 8 `Set`
nodes, whose JSON becomes the webhook's HTTP response. Common/recurring
fields: `lead_status`, `lead_name`, `lead_mail`, `lead_phone`, `source:
"Email"`, `response` (HTML or plain SMS text, or `null` for silent/
escalation branches), `message_id`, `create_lead`, `update_lead`,
`parent_id`, `email_subject`, `request` (the cleaned customer message),
`fe_lead_status`, `response_mode` (`email` or `sms`), and (where
applicable) `preferred_communication_mode_selected/mode/old_messageID`.
Branch-specific extras: `booking_status`/`booking_date`/`booking_time`
(booking path); `vin`/`make`/`model`/`year`/`Lead_Source` (ADF paths);
`send_user_response`/`send_manager_sms`/`manager_sms`/`user_response` (DND
and Managerial Review paths); `sender_number`/`recipient_number` (DND
path).

**Key integrations/side effects:**
- **OpenAI (via LangChain agent + `lmChatOpenAi` credential nodes):** 17
  agent calls total, all `gpt-4o-mini` except `Response Generation for
  Phone Lead1` (SMS drafting for non-ADF phone leads), which uses
  `gpt-3.5-turbo`.
- **MongoDB:** 6 queries — `users` (dealer/store config), `vehicles` x3
  (inventory lookup by dealerId+VIN, by dealerId+make/model, and by
  dealerId+VIN-from-lead-record), `emails` (prior SMS thread lookup),
  `leads` (VIN previously associated with a lead).
- **No outbound HTTP/Twilio/SES calls exist in this workflow** — purely a
  decisioning/content-drafting engine.
- **Booking URLs** are constructed inline in several prompts as
  `https://www.autopulse.ai/booking/{dealer_id}/{lead_id}`.
- **Notable bugs/inconsistencies worth flagging to a developer:**
  1. `Cleaning the Email`'s code references a non-existent node
     `$node["Decoding"]` instead of `Decoding Mail Content` (same issue as
     workflow-3).
  2. `Set FE Lead Status2` checks for the misspelled status `"Appointment
     Bookedt"`, so the non-ADF SMS phone-lead branch can never correctly
     flag a booked appointment.
  3. `Visit Response Formatting` sets `response_mode: "sms"` while
     populating `response` from an HTML-email-formatted node (`Wrap
     HTML1`) — a mismatch between content format and declared channel.
  4. The `Response Generator` prompt references `$node["Format"]
     ["category"]`, a field `Format` never actually sets.

## workflow-10.json — WriteWithAI
================================================================================

**Purpose:** An AI-drafting endpoint for AutoPulse's CRM. Given a lead's
conversation thread, a dealer's instruction/prompt, and the target channel
(SMS, email, or internal note), it builds a channel-and-language-aware
prompt, sends it to GPT-4o-mini to generate a draft customer reply, parses
the model's JSON output, and returns the draft (plus subject and customer
name) to the caller. Used to power an "AI-assisted reply drafting" feature
for sales agents responding to leads.

**Trigger:** Webhook, `POST /write-with-ai` (`responseMode: lastNode`).
Workflow is **active**.

**Flow graph:**
```
WriteWithAI Trigger -> Context Builder -> Message a model -> JSON Parser -> Response Formatting
```

**Step-by-step:**
1. **WriteWithAI Trigger** (`n8n-nodes-base.webhook`, v2) — `POST
   /write-with-ai`. Expects a JSON body shaped like: `{ lead: {...},
   dealerName, channel, language, thread: [{date, direction, subject,
   body, attachments}], prompt }`.
2. **Context Builder** (`n8n-nodes-base.code`) — JS logic that:
   - Reads `input = items[0].json.body` and pulls out `thread` (array),
     `prompt`, `channel` (defaults `"email"`, lowercased), `language`
     (defaults `"English"`), `lead` (object), and `lead.name` trimmed into
     `customerName`.
   - Sorts `thread` chronologically by `date`.
   - Builds a `conversation` string from the **last 6** messages,
     formatting each as `Customer: <body>` (if `direction === "IN"`) or
     `Agent: <body>` (otherwise), whitespace-collapsed.
   - Builds a `leadContext` block with Customer Name, Vehicle Interest,
     and Dealer name.
   - Builds a `nameInstruction`: if `customerName` is present, instructs
     the model to always address the customer by name; otherwise instructs
     it not to invent a name and use a generic greeting.
   - Builds a `channelInstruction` based on `channel`:
     - `sms`: reply must be under 160 characters, concise/action-oriented,
       no signature.
     - `email`: structured professional email with greeting/closing,
       encourage next step.
     - `notes`: internal note only, no greeting/customer tone, summarize
       intent + next action; also sets `useContext = false`.
     - any other value: no specific instruction added.
   - Assembles `finalPrompt`: if `useContext` is true and there's a
     non-empty `conversation`, includes the language, lead context,
     conversation history, the dealer's `prompt` instruction, name rules,
     channel rules, and a goal of being natural and moving toward
     appointment booking. Otherwise uses a shorter template without
     conversation history.
   - Returns `{ finalPrompt, channel, language, customerName }`.
3. **Message a model** (`@n8n/n8n-nodes-langchain.openAi`, v2.1) — calls
   OpenAI model `gpt-4o-mini` with:
   - System message: instructs the model to return **only** valid JSON of
     the form `{"draft": "...", "subject": "...", "name": "..."}` (subject
     only for email, else empty).
   - User message: the `finalPrompt` plus "Output strictly in JSON
     format."
   - `onError: continueRegularOutput` — errors don't halt the workflow.
4. **JSON Parser** (`n8n-nodes-base.code`) — extracts the raw model text,
   regex-extracts the first `{...}` JSON blob (tolerating extra text
   around it), parses it; on parse failure, falls back to treating the raw
   text itself as the draft with empty subject/name.
5. **Response Formatting** (`n8n-nodes-base.set`, v3.4) — assigns three
   string fields onto the output item, effectively passing them through:
   `draft`, `subject`, `name`.

**Final outputs:** Since `responseMode` is `lastNode`, the webhook responds
with `{ draft, subject, name }` — the AI-drafted reply text, an email
subject (if applicable), and the customer name used.

## workflow-11.json — Multilingual_translation
================================================================================

**Purpose:** A batch text-translation endpoint. It accepts a list of
messages plus a target language, translates each message's text
independently via GPT-4o-mini, and returns the translations keyed by the
original message IDs. Used to power multilingual messaging in the AutoPulse
CRM (e.g., translating lead conversation threads).

**Trigger:** Webhook, `POST /translation` (`responseMode: responseNode`,
meaning the response is explicitly produced by a downstream "Respond to
Webhook" node). Workflow is **active**.

**Flow graph:**
```
Translation (webhook)
  -> Flatten Messages
      +-> Merge (input 0)
      +-> Get Translated Text -> Merge (input 1)
  -> Merge (combine by position)
  -> Building Response
  -> Respond to Webhook
```

**Step-by-step:**
1. **Translation** (`n8n-nodes-base.webhook`, v2) — `POST /translation`.
   Expects body `{ messages: [{id, text}, ...], targetLanguage }`.
2. **Flatten Messages** (`n8n-nodes-base.code`) — converts the single
   incoming webhook payload into **N separate items** (one per message),
   each carrying `id`, `text`, `targetLanguage`. This fans out downstream
   processing to per-message items.
3. From here the flattened items branch two ways in parallel:
   - Straight to **Merge** input 0 (the untranslated original item).
   - Through **Get Translated Text** (`@n8n/n8n-nodes-langchain.openAi`,
     v2.1) — calls `gpt-4o-mini` per item:
     - System message: "You are a translation engine. Translate text
       accurately. Return ONLY the translated text. Do not explain
       anything."
     - User message: `Translate the following text into
       {{$json.targetLanguage}}:\n\n{{$json.text}}`
     - Output feeds into **Merge** input 1.
4. **Merge** (`n8n-nodes-base.merge`, v3.2) — mode `combine`, `combineBy:
   combineByPosition`, `includeUnpaired: true`. Pairs up each original
   flattened item (input 0) with its corresponding OpenAI translation
   result (input 1) by list position.
5. **Building Response** (`n8n-nodes-base.code`) — iterates all merged
   items and builds a single output item containing a `translations` array
   of `{id, translatedText}` pairs, pulling the translated text out of the
   OpenAI response shape.
6. **Respond to Webhook** (`n8n-nodes-base.respondToWebhook`, v1.4) —
   `respondWith: json`, `responseBody: {{$json}}` — returns the item
   produced by Building Response as-is.

**Final outputs:** The webhook responds with `{ "translations": [ { "id":
<message id>, "translatedText": "<translated string>" }, ... ] }`, one
entry per input message, matched by original ID.

## APPENDIX: Anomalies / likely bugs found across all workflows
================================================================================

These were noticed incidentally while mapping each workflow's node graph —
none were the target of the analysis, so treat them as leads to verify
against actual n8n execution logs, not confirmed defects.

1. **workflow-3.json / workflow-9.json** — `Cleaning the Email` (ADF
   branch) references a non-existent node `$node["Decoding"]`; the actual
   node is named `Decoding Mail Content`, which runs *after* it. Likely a
   leftover reference from a node rename.
2. **workflow-3.json** — `Set Bot Name & Store No & Store Name & Store
   Address`'s `Trade Link` and `Credit Finance` field expressions are
   missing a closing `}}`.
3. **workflow-3.json** — the video-attachment analysis path's aggregated
   `video_intelligence` output is likely discarded by the subsequent
   `cleanup` Execute Command node (which typically replaces its input JSON
   with `{stdout, stderr, exitCode}`), and even if it survived,
   `Aggregate AI Insights` has no handling branch for `modality ===
   "video"` — so video attachment analysis currently never reaches the
   reply-generation prompts.
4. **workflow-3.json / workflow-9.json** — `Set FE Lead Status2` checks for
   the literal string `"Appointment Bookedt"` (typo, trailing "t") instead
   of `"Appointment Booked"`, so the non-ADF SMS phone-lead branch can
   never correctly report a booked appointment via that node.
5. **workflow-9.json** — `Visit Response Formatting` sets `response_mode:
   "sms"` while populating `response` from an HTML-email-formatted node
   (`Wrap HTML1`) — a mismatch between declared channel and actual content
   format.
6. **workflow-9.json** — the `Response Generator` prompt references
   `$node["Format"]["category"]`, a field `Format` never actually sets.
7. **workflow-4.json** — `Format Inventory Summary`'s JS has a missing
   comma between two object properties (`price: ... null` then
   `shortUrl:` with no separator) — a JavaScript syntax error that would
   throw at runtime, breaking the returning-customer/VIN-lookup path
   entirely. Also stores the field as `shortUrl` rather than `vdplink`
   (nothing downstream reads `shortUrl`), so even if fixed, no VDP link
   would reach the customer despite the workflow's "(VDP URL)" name.
8. **workflow-6.json** — `Intent Response Bank`'s static `jsonOutput`
   string is malformed JSON: two JSON objects concatenated back-to-back
   instead of merged into one (`{"A":...,"B":..., {"C":...} }`) — likely
   fails to parse/set correctly at runtime.
9. **workflow-2.json** — a `Check if translation is needed` ->
   `Managerial Review Translation` -> `Managerial Review Format` sub-chain
   exists to translate the canned Managerial-Review holding message into
   the customer's detected language, but has **no inbound connection**
   from the rest of the graph — dead/unreachable code. Non-English
   customers currently receive the English canned text.
10. Across workflow-2/3/7/8/9: none of the LLM "agent" nodes use n8n's
    structured-output parser — every prompt is instructed to return raw
    JSON text which downstream Code/Set nodes manually
    `JSON.parse()` (after stripping markdown fences/newlines). Malformed
    LLM output breaks whichever branch was executing, with no shared
    fallback/retry logic.
11. workflow-2.json's attachment pipeline writes fixed temp-file paths
    (`/tmp/input.pdf`, `/tmp/output.txt`, `/tmp/input_video.mp4`,
    `/tmp/frame_*.jpg`) — concurrent webhook executions on the same n8n
    worker could race/clobber each other's temp files. The same pattern
    exists in workflow-3.json's attachment pipeline.
