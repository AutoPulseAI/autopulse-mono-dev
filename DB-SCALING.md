# AutoPulse – DB Scaling

Goal: MongoDB handles 10k+ AI write requests/min, plus dashboards. Live DB untouched; all testing on the dev servers.

## AWS resources (us-east-1)

| Instance | Type | Role |
|---|---|---|
| Autopulseapp | t2.xlarge (4 vCPU, 16 GB) | Live web server: CRM, AI, Redis, chatbot app |
| database | t2.large (2 vCPU, 8 GB) | Live MongoDB **8.0.19** (standalone, `emailai`) — private `172.31.16.69:27017`, reachable only from the app server |
| AutopulseAI | t2.large | Live chatbot brain + Postgres + MySQL |
| Autopulsemail | t2.medium | Mail server (to confirm) |
| dev application | t2.medium (4 GB) | Test: MongoDB PRIMARY |
| dev ai server | t2.medium (4 GB) | Test: MongoDB SECONDARY + ARBITER |

## Solutions

1. **Indexing** – compound indexes, `dealer_id` first, ESR rule; hide → drop unused indexes.
2. **Query optimization** – `.lean()`, projections, `$facet`, cursor pagination; identical results, verified by tests.
3. **Connection pooling** – CRM web 50, CRM worker 20, AI API 20, AI worker 50 (~140 total).
4. **Redis caching** – dashboards (short TTL), dealer profiles (cleared on update); never compliance data.
5. **Replica set (PSA)** – primary on dev application, secondary + arbiter on dev ai server; 3 data nodes for production.
6. **Read/write split** – ✅ **DONE** (owner, 2026-11-18). Dashboards/reports read off the secondary via the connection string (`&readPreference=secondaryPreferred`, `maxStalenessSeconds: 90`); AI, compliance, inventory, bookings, conversations stay on primary. Wired at the URI/env level (not app code), consistent with `reports-reconcile.js` using `secondaryPreferred`.
7. **Bulk writes** – `ordered:false`, batches of 500–1,000 (campaigns, DealerVault).
8. **Write concern** – `w:1` in test; `majority` + `wtimeout` once there are 3 data nodes.
9. **Queue buffering** – ✅ **DONE** (2026-11-20). Env-driven BullMQ rate caps on the write-heavy CRM workers (safety valve), + SAQ caps already present on the AI side. Campaign blast (the flood source) capped at `CAMPAIGN_RATE_PER_MIN` (default **160000**/min = top of the DB's proven healthy zone); email/sms/lead backstopped at `EMAIL_/SMS_/LEAD_RATE_PER_MIN` (default 30000 each; low-concurrency so can't realistically flood). Set any `*_RATE_PER_MIN=off` to disable. AI side was already throttled: `WORKER_CONCURRENCY` (20) + `DEALER_MAX_INFLIGHT` (10) + lead locks + busy-retry. Helper: `app/worker/rateLimit.js`.
10. **Compression** – ✅ **DONE (2026-11-23).** Snappy **network** compression already active between nodes by default (verified live on primary: snappy compressor ~10.4 GB in → ~8.9 GB out; zstd/zlib unused). zstd **storage** deliberately skipped — collections already snappy-compressed by MongoDB 8 default, disk ~60% used, zstd only adds CPU for no needed gain. No config change, no restart.
11. **Server tuning** – ⚪ **NOT MANDATORY / cutover-time, sized to the real prod box.** Checked the test primary (2026-11-23): FS = **ext4** (not XFS — XFS is only a mild preference, switching needs a destructive reformat of the root volume, not worth it; **does NOT affect data or data types**), WiredTiger cache = **0.5 GB** (deliberately low on this 3.8 GB no-swap t2.medium test box), disk = one 50 GB root volume (gp3 IOPS = EC2-console setting). These are **per-box settings sized to that box's RAM/disk**, and the test box ≠ the live t2.large — so tuning numbers don't carry over. **Cutover note:** when building the fresh prod DB box, put the data volume on **XFS from the start** and restore the dump into it (no conversion, no risk), set cache ≈ half the box's RAM, confirm gp3 IOPS. Nothing to do on the test box.
12. **Monitoring** – ✅ **DONE (2026-11-23).** rs0 **primary + secondary**: queryable profiler turned ON (`db.setProfilingLevel(1, {slowms:100})`, `emailai`, each node — was 0, node-local so set per box). **Live DB**: `ravi` is app-only (no admin/profiling privilege — same block as `$indexStats` in the Nov-13 audit; no admin Mongo user on record), so the profiler can't be enabled there, BUT the live mongod **already logs every slow query >100 ms to its log file by default** (the same source the Nov-13 audit used) and that log is readable on the `database` box — so live is monitored via the log file, zero prod change. All three boxes capture ">100 ms" slow queries → comparable during the dual-write window. _Runtime caveat: the rs0 profiler level resets to 0 on a mongod restart; re-enable, or add `operationProfiling.mode: slowOp` to `mongod.conf` to persist. Richer live monitoring (queryable profiler + `$indexStats`) needs a `clusterMonitor`/admin user — tracked in `DB-UPSCALING-BACKLOG.md`._
13. **PM2 cluster** – ⚪ **FUTURE / conditional (not part of this DB-scaling pass).** This is CRM **web-app** scaling, not DB. Node uses one CPU core per process; the app server (t2.xlarge, 4 cores) runs a single CRM process. Cluster mode forks N copies to use all cores — but **only do it if a load test shows CRM CPU >70%** (it isn't today; the bottleneck work was always the DB). **Prerequisite before clustering:** make the 3 in-process crons and the `aiMode` in-memory cache cluster-safe first (else N copies run each cron N times and the cache desyncs). Parked for the future.

**Future:** more replicas, sharding by `dealer_id`, auto scaling, MongoDB 8.0 upgrade, **adaptive (auto-scaling) rate limiting** — #9's rate cap reacting live to DB health (CPU/pool/replication lag) instead of a fixed env number; deferred (more moving parts + needs re-testing; not worth it while ~9× headroom exists).

**Process:** baseline load test → one step at a time → re-measure → keep only what the numbers prove.

## Security hardening — DEFERRED to production cutover

The DB-scale cluster is intentionally left permissive during build + load/pressure testing. **Before shifting any production traffic here, complete ALL of these:**

- Close MongoDB **27017** to the internet: on the dbscale security group(s) remove the `0.0.0.0/0` rule; allow 27017 only between the two private IPs (`172.31.28.18`, `172.31.38.100`) + the app server.
- Restrict **SSH (22)** to known admin IPs (currently `0.0.0.0/0`).
- Remove leftover world-open ports from the old dev boxes if unused (`11434` Ollama, `5000`, `80`, `443`).
- **Rotate the Mongo password** — the test cluster currently reuses the live `ravi` password; give production its own.
- Re-confirm `bindIp` private-only, auth ON, keyfile in place. _(Version upgrade to 8.0.38 / FCV 8.0 completed 2026-11-12 — see progress log.)_
- **Open the secondary box's security group to the app server on 27017** (`172.31.82.184/32`). _Found during load testing 2026-11-19:_ the app server could NOT reach `172.31.38.100:27017/27018` (its SG only allows the primary box `/32`), so when the replica PRIMARY role floated to that box, the app got "No primary available for writes." The app must reach **every** data node, because the primary role floats between them.
- **Revert the temporary election-priority change.** During the 2026-11-19 outage, `172.31.28.18` was pinned to `priority: 10` (others 1, arbiter 0) via a forced `rs.reconfig`, so the app-server-reachable node would hold PRIMARY during testing. Once the SG above is opened, reconfig priorities back to equal (`1`).
- **Consider moving the arbiter off the secondary box.** The data secondary and the arbiter both run on `172.31.38.100`, so that one box holds 2 of 3 votes — if it drops, the set loses quorum and goes read-only (this is what happened 2026-11-19).

_Owner decision 2026-11-12:_ keep `27017` open to `0.0.0.0/0` during load/pressure testing (auth stays ON, so a password is still required). Risk accepted for the test phase only.

## Cutover — dual-write (shadow) validation plan

**Goal:** prove the optimizations hold on real traffic *before* betting production on rs0. Keep the live `database` box as the real source of truth; mirror writes onto rs0 and compare for a few days.

**How (owner's plan, 2026-11-23):**
1. **Seed rs0 full** — copy all live data onto the rs0 primary first (mongodump→mongorestore), so rs0 starts as a complete clone, not just new writes. (Already done once 2026-11-12; re-sync fresh at the start of the shadow window so there's no gap.)
2. **Dual-write** — on every write, the app writes to **both** the live DB (as today) and the rs0 primary. Reads stay on live (authoritative). For a few days it's a bit slower (each write waits on two DBs) — accepted.
3. **Fail-safe is mandatory** — the rs0 (shadow) write MUST be wrapped so that if rs0 is slow/down, the **live write still succeeds and the app never breaks/stalls**. Live = source of truth; shadow may lag or fail silently (log it, don't throw). Never let a shadow hiccup touch production latency or correctness.
4. **Watch both** (see #12 Monitoring) — slow-query profiler, `$indexStats`, replication lag, CPU/credits, connection counts on **both** live and rs0, plus a shadow-write success/lag/error counter.
5. **Compare** — over the window, confirm rs0 keeps up with real write volume (0 dropped once seeded), query results/numbers match live, and latency/index behavior is what the optimizations predicted. Decide what still needs tuning.
6. **Flip** — only once the numbers prove it: point reads+writes at rs0, retire the shadow path.

**Caveats to respect:** (a) seed-then-dual-write must together keep rs0 *complete* — a comparison that looks wrong may just be rs0 missing pre-shadow data; (b) dual-write mainly proves two things — rs0 survives real write volume, and queries come out identical; (c) finish the security-hardening checklist above before the flip. **Alternative to app-level dual-write (if code changes are unwanted):** cluster-to-cluster sync (`mongosync`) or joining rs0 nodes to the live set — evaluate at cutover.

Full detail + before/after numbers in `INDEXING-PLAN.md`. Two things the person doing the cutover must know:

2. **If you re-dump fresh data from the old DB at cutover, `mongorestore` brings back ALL the old indexes** — including the old `$type:'string'` unique indexes and the 15 redundant ones we removed. So after any fresh re-sync, re-run two cleanups on this cluster:
   - **`$type → $exists` migration:** `db.emails.dropIndex('ai_idempotency_key_unique')` and `db.ai_messages.dropIndex('idempotency_key_1')`, then let the app recreate them as `$exists:true` (or create by hand: `partialFilterExpression:{<field>:{$exists:true}}`, `unique:true`).    - **The 15 redundant drops** (list in `INDEXING-PLAN.md §C`) — a fresh restore reintroduces them; drop them again.

   If this cluster keeps the data it already holds (no re-dump), there is nothing to redo — the index set is already correct.
