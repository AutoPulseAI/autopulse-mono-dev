# Frontend Implementation Plan — Phase Plan 1

Who this is for: whoever builds the frontend side of the AI layer. Written in
plain English on purpose — this is a plan to follow, not a technical
reference. For the "why" behind any of this, see
[`../../architecture/architecture.md`](../../architecture/architecture.md),
[`../../architecture/STACK.md`](../../architecture/STACK.md), and
[`../../architecture/APIS.md`](../../architecture/APIS.md).

---

## The one rule that shapes everything below

**We are not building a new app.** The dealer portal already exists (it's
the Next.js app under `aidmvcs-be-dev/app/dealer/`), it already has an
inbox, a lead list, a booking calendar, and a customer page. Almost
everything the AI layer needs to show up on screen belongs on those existing
pages — not a new one.

The only genuinely new page is a small review screen for approving/rejecting
product recommendations (Phase 5). Everything before that is additions to
screens that are already built and that staff already look at every day.

**The second rule: the browser never talks to the AI service directly.**
Every request goes: browser → the dealer portal's own backend (a Next.js API
route) → the AI service. The dealer portal's backend is what checks "is this
person actually logged in and allowed to see this dealer's data" before
anything reaches the AI service. Never call the AI service's address straight
from a page or a component. This is explained in full in `INTEGRATION.md`,
but the short version is: this rule protects real customer data, so it's not
optional.

**The third rule: build against what's actually working, not what's
planned.** `APIS.md` marks each thing as **live** or **planned**. Do not
start wiring up a screen to a **planned** endpoint — it doesn't exist yet.
Each phase below says which of the two it needs.

---

## Phase overview

| Phase | What it adds | Needs from the backend |
|---|---|---|
| 1 | Make it obvious in the existing inbox which messages the AI wrote | Nothing new — just a marker on existing messages |
| 2 | A place for staff to catch and fix a reply the AI wasn't allowed to send | The **planned** conversation endpoint, once it's live |
| 3 | Let staff see what the AI actually remembers about a customer | The **planned** conversation endpoint's memory data, once it's live |
| 4 | Show staff when/why a "customer went quiet" follow-up was sent | The **planned** silence-check endpoint, once it's live |
| 5 | A real screen for approving/rejecting product recommendations | The `/upsell/recommend` and `/upsell/feedback` endpoints — already live today |

Phases 1–4 are all about the *qualification conversation* work (the bot that
answers questions, looks up inventory, books appointments). Phase 5 is the
separate, smaller "recommend a product" capability, which is further along
on the backend today, so it's realistic to build sooner even though it's
listed last.

## Phase 1 — Show which messages the AI wrote

**Goal:** a manager looking at the existing inbox should be able to tell, at
a glance, "this reply was written by the AI" versus a message a staff member
typed themselves. Right now there's no way to tell them apart.

**Where:** the existing conversation/inbox screens
(`app/dealer/conversations/`, and anywhere else a message thread is shown,
like the lead detail view).

**What to build:**

- A small, clear label or badge next to any message that was generated by
  the AI layer (not a manual staff reply). Something as simple as a tag that
  says "AI" is enough — this doesn't need to be fancy, it needs to be
  unmissable.
- When a message has a reasoning trace attached to it (see `FRAMEWORKS.md`'s
  section on tracing), show a small "why did it say this" link or icon next
  to that message. Clicking it can open the trace in a new tab for now — it
  doesn't need its own custom viewer in phase 1. If there's no trace
  available for a given message, don't show the link.

**Why this is first:** it costs almost nothing to build (it's a read-only
label on data that already exists) and it's the single most useful thing for
building trust with the people using this — before anything else is built,
staff should already be able to see the AI's work happening in the place
they already look.

**What this phase does NOT need:** any new backend endpoint. This only reads
data that's already there once messages start getting tagged with where they
came from — confirm with the backend team exactly which field marks a
message as AI-generated before starting.

## Phase 2 — A place to catch replies the AI wasn't allowed to send

**Background, so this makes sense:** per `architecture.md` §7 and §10, before the AI
sends anything, it checks itself for two kinds of mistakes — a wrong fact, or
wrongly refusing to help. If either check fails enough times, the AI is not
allowed to just send something anyway. Right now, nothing on screen shows
what happens to that blocked reply — a real person needs to be able to catch
it and either fix it or send it themselves.

**Where:** a new tab or filter inside the existing lead list or conversation
inbox — not a whole new page, just a new way to filter the list staff
already look at (similar to how leads can already be filtered by status).

**What to build:**

- A filter/tab called something like "Needs review" that shows any
  conversation where the AI has paused and is waiting for a person. Since
  architecture revision 3 there are four reasons this happens, and the list
  should show which one it is:
  - **the reply failed its checks** too many times (wrong fact, wrongly
    refused to help, or not well enough supported),
  - **the AI wanted to take a real action on its own** (e.g. book an
    appointment the customer didn't clearly ask for),
  - **a spending/looping limit was hit**,
  - **the customer's message looked like an attempt to manipulate the bot.**
- When staff open one of these, show: the customer's last message, what the
  AI wanted to send or do, and — in plain words — why it stopped
  (e.g. "this reply stated a trade value that the customer never gave us").
- Give staff three simple options: **send it anyway** (if the block was a
  false alarm), **edit it and send** (fix the specific problem, then send),
  or **write a reply from scratch** (the existing manual-reply box already
  does this, just reuse it).
- Whatever staff choose should be recorded somewhere retrievable later —
  this is exactly the kind of real-world case that should eventually turn
  into a test case for the backend's automated checks, so don't let it just
  disappear once handled.

- When staff decide, the AI **picks up exactly where it paused** — it doesn't
  start the conversation over. The screen only needs to send the decision.

**Depends on:** the planned `GET /qualify/reviews` and
`POST /qualify/reviews/{review_id}/decide` endpoints in `APIS.md`. Don't start
this phase until they're live; there's nothing to show yet.

## Phase 3 — Show what the AI actually remembers about a customer

**Background:** per `architecture.md` §5, the AI is supposed to remember
specific things about a customer — what cars were shown to them, what they
said about their budget or trade-in, and when they said it. Right now
there's no way for a human to check any of that.

**Where:** the existing customer page (`app/dealer/customers/[id]/`), as a
new tab or section alongside what's already there (past sales, service
history, etc. — this fits right in with what that page already shows).

**What to build:**

- A simple timeline: what the customer said, what the AI showed them
  (specific cars, specific answers), and when — in order, with real
  timestamps.
- Clearly separate "things the customer told us" from "things we looked up
  for them" — these are different kinds of facts and staff should be able to
  tell which is which at a glance.
- If a fact looks old (the backend will flag stale information, per
  `architecture.md` §5.4), show that clearly too — e.g. a faded/greyed-out
  style, or a small "this was said 3 months ago" note. This matters because
  staff shouldn't assume an old answer is still true any more than the AI
  should.
- Show facts that were **replaced**, not just the current ones — e.g. "Budget:
  $25k (said today) — replaced $30k (said 3 weeks ago)". Staff need to see
  that the customer changed their mind, not just the latest value.
- For every fact, show **where it came from**: "customer said this" (with a
  link to the exact message), "looked up in inventory on [date]", or "the AI
  worked this out from the customer's message". Per `architecture.md` §5.3,
  the AI's own guesses are never saved as facts, so they should never appear
  here — if one does, that's a bug worth reporting.

**Depends on:** the planned conversation endpoint's memory data being real
and queryable. Until then, this phase has nothing to display.

## Phase 4 — Show when a "gone quiet" follow-up was triggered

**Background:** per `architecture.md` §11, if a customer stops replying for
too long, the AI writes a summary of the conversation and hands it to the
existing follow-up system, which decides when/how to actually reach back
out. Staff should be able to see that this happened and why, not have a
follow-up message appear with no explanation.

**Where:** the lead detail view, near wherever follow-up activity is already
shown (there's likely already something here for the platform's existing
follow-up system — check before building something that duplicates it).

**What to build:**

- A note on the lead showing: when the customer went quiet, what summary the
  AI wrote about the conversation at that point, and which follow-up
  channel was chosen (text vs. email) and why (e.g. "customer's stated
  preference" or "only channel we have permission to use").
- This is read-only. Staff aren't expected to act on it here — the existing
  follow-up system already owns sending it. This is purely "let a human see
  why this happened."

**Depends on:** the planned silence-check endpoint being live and actually
producing these summaries.

## Phase 5 — The product-recommendation review screen

**Background:** this is the separate, smaller capability — the AI
suggesting a specific paid product (like an extended warranty) after some
event, not the ongoing conversation work above. This is further along on
the backend already (`/upsell/recommend` and `/upsell/feedback` both exist
and are tested), so it's realistic to build this screen sooner than Phases
2–4, even though it's listed last here.

There's already a placeholder page for this
(`aidmvcs-be-dev/app/dealer/upsell/page.js`) — it exists but has no real
content yet, and it isn't linked in the sidebar on purpose (an empty page in
the nav looks broken). Do both — build the page, then add the sidebar link —
in the same piece of work, not separately.

**What to build:**

- A list of pending recommendations for a customer: what's being
  recommended, the price, and — importantly — the AI's stated reasoning for
  why (this should always be shown, never hidden behind a click; if the
  reasoning looks weak or generic, that's useful for staff to notice).
- For each one, three actions: **approve** (send as recommended), **edit**
  (change something, then send), **reject** (don't send this one). Whatever
  is chosen gets sent back to the backend — this is what teaches the system
  not to keep suggesting something a customer has already turned down.
- Add the link into the sidebar navigation once this page actually has
  content — not before.

**Depends on:** nothing new — `/upsell/recommend` and `/upsell/feedback` are
already live today. This phase can start immediately.

## API contracts the frontend must follow

These are the rules, not suggestions — breaking any of these either won't
work or will create a real security problem.

1. **Never call the AI service's own address from the browser.** All calls
   go through the dealer portal's own backend routes (under
   `app/api/upsell/*` today; more will be added as Phases 2–4 need them).
   Full reasoning in `INTEGRATION.md`.
2. **Every request to those routes needs the user to actually be logged in**
   as a dealer/agency/admin — this already happens automatically the same
   way it does for every other page in the dealer portal; nothing extra to
   build, just don't bypass it.
3. **Match the request/response shapes exactly as documented in
   [`../../architecture/APIS.md`](../../architecture/APIS.md).** That file
   is the source of truth for every field name and whether an endpoint is
   live yet — if a field isn't listed there, don't assume it exists.
4. **Endpoints marked "planned" in `APIS.md` are not real yet.** Check with
   the backend team before starting any phase that depends on one — building
   UI against a shape that later changes is wasted work.
5. **Specifically, for what's live today:**
   - `POST /api/upsell/recommend` — send `dealer_id`, `customer_id`, an
     optional `lead_id`, and a `trigger` string. Get back a list of
     recommendations (each with a type, a price, and reasoning) or an empty
     list with a reason why nothing was recommended.
   - `POST /api/upsell/feedback` — send which recommendation, the decision
     (`approved` / `edited` / `rejected`), and an optional staff note. Get
     back confirmation plus which product types are now temporarily
     suppressed for that customer.
6. **When a new "planned" endpoint goes live, this document should be
   updated** (or a `FPLAN_2.md` started) rather than quietly building ahead
   of what's documented — keep the plan and the real backend in sync.
